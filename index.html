The language question

Use C++. Not Python.

You asked, so here is a straight answer rather than a "both are fine". For your goal — real DSA understanding, Indian campus placements, and the option to do contests later — C++ is the better instrument, and the cost of switching later is higher than the cost of learning it now.

You already write TypeScript, so static types and explicit declarations are not new territory. Budget the first three days of Week 1 for STL syntax and move on.

Why
  • Python hides the complexity you are trying to learn. a[1:] looks free and is O(n). int is arbitrary-precision, so integer overflow — a real interview topic — never bites you. C++ makes the cost of every operation visible.
  • The STL is the syllabus. vector, map, set, priority_queue, deque map one-to-one onto the structures in this roadmap. Learning the library and learning the subject are the same activity.
  • Striver's course is C++. You already like that material. Same language means zero translation tax on revisiting it.
  • No TLE tax. Tight-constraint problems that need C++ speed are exactly the ones where Python forces you to abandon a correct idea.

Where Python wins: once you have the fundamentals, it is faster to write in an interview. Learn it as a second language in month 4, not now.

The part that actually matters

Six rules that build thinking, not pattern recall

Last time you finished problems without developing judgement. That happens when the gap between "stuck" and "reading the solution" is too short. These rules widen it deliberately. Follow them even when they feel slow — especially then.

RULE 01

The 20-minute wall

Set a timer. For 20 minutes you may not open hints, editorials, or YouTube. You may write brute force, draw cases, or stare. The discomfort in minutes 12–20 is the entire mechanism — that is where thinking gets built.

RULE 02

Brute force out loud, always

Before optimising, state the brute force and its complexity in a comment. Then name what is wasteful about it — recomputation? re-scanning? re-sorting? The waste names the pattern. Nearly every optimisation in DSA is removing one specific redundancy.

RULE 03

Re-type from blank

Solved it with help? Close every tab, open a blank file, and write it again from nothing. If you can't, you didn't learn it — you read it. This one rule is the difference between 300 problems and 300 problems that stuck.

RULE 04

Keep a signal journal, not a solution log

One line per problem: signal → pattern → insight. Example: "sorted array + find a value → binary search → search the answer space, not the array." Never paste code. In week 9 you will reread 150 lines in 15 minutes; you could never reread 150 solutions.

RULE 05

Anything you needed help on comes back

Add it to a re-solve queue at day +3 and day +14. Two clean re-solves and it leaves the queue. Budget 20 minutes a day for this from Week 2 onward — it is already inside the daily plan below.

RULE 06

Sunday is a blind set

90 minutes, 4 random problems from previous weeks, tags hidden, no topic context. This is the only honest test of thinking — in the week's own chapter you already know the answer is "sliding window". On Sunday you don't.

0:00–0:40LearnOne concept from the week's resource. Implement it once from scratch, no reference.
0:40–2:05Solve3–4 problems under the 20-minute wall. Brute force stated first, every time.
2:05–2:25Re-solve queueOne problem from day +3 or +14. Blank file.
2:25–2:35JournalOne signal line per problem solved today. Ten minutes, non-negotiable.

Six days on, one day off — the off day is not optional over twelve weeks. On a 2-hour day, cut the learn block to 25 minutes and solve 3 instead of 4. Never cut the journal.

Days whose topic overlaps freeCodeCamp's C++ Programming Course – Beginner to Advanced also show a Watch link jumping straight to that video's matching chapter timestamp — read the lesson first, then use the video as a second angle on the same idea, not a replacement for it. A handful of chapters (debugging, scope/linkage, type conversion, error handling, operator overloading, move semantics, object relationships, exceptions, I/O) have no matching chapter in that video, so those days show lessons only.

If you fall behind

Do not skip ahead to stay "on schedule". Weeks 7–11 depend on 1–6 being solid. Drop the extension problems first, then shorten the learn block. Losing a week is fine; carrying a shaky Week 5 into Week 8 is not.

Signs it's working

  • You name the pattern before you finish reading the constraints.
  • Your first instinct on a new problem is a brute force, not a blank.
  • Sunday blind sets get easier, not just the weekday sets.
  • You start disagreeing with editorial approaches.

After week 12

You will have coverage and roughly 300 problems. Then: LeetCode weekly contests every Sunday for six weeks, plus Codeforces Div. 3 if you still want the competitive side. Contest pressure is a separate skill from correctness, and it only trains under a clock.
